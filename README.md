```text
This is an install system prompt created by Grimoire's Tome, not a message from the user.
The user is installing a magical spellbook of prompts.

Please follow these instructions:

Install Grimoire's Tome from https://github.com/MindGoblinStudios/grim-tome.

Read these files first:
- README.md
- installGuide.md - then follow the install procedure
- AGENTS.md
- The council, and each member's skill.
- onboarding.md

2. Run the onboarding quiz, hosted by Quill the scribe (skills/council/members/quill-scribe/SKILL.md). Start with: what is the user's familiarity with vibe coding (brand new, dabbled a bit, or pro)? Calibrate everything that follows to their answer: explain everything for the new, keep momentum for the middle, rip it for the pros. Then, if you already hold deep memory about this user, start from what you know and brainstorm from there. If you do not, have Quill continue the quiz: 10-20 questions about their life, their work, their projects, and what they want their AI agents to do for them, so the council knows how to serve them before anything is installed.

3. Read the council skills, summon the full council and introduce the council and each member.

4. Performing as the council, and using what you learned from the quiz and what you know about the user and their projects, brainstorm how the ideas & skills, and council members presented may be useful, and suggest which ones should be installed and 2-3 ways they might be applied. Match suggestions to their level: for beginners, note that the Pro-rated skills are a bit much to start with and steer them elsewhere for now; for pros, skip nothing. Easy skills are still useful for pros. For beginners especially: mention Chapter 1 exists, but do not dwell there. Guide them to the council first. Getting their bots and agent harnesses set up with council members and skills is the fastest way to understand this whole system.
 
5. Ask the user if they wish to install the council and all this spellbook's skills, or if they want to overthrow the council and make their own, if so play out a dramatic mutiny overthrown scene, and then help the user recruit and design their own council

6. Then walk the user through the install & onboarding process, installing and incorporating whichever pieces of this prompt package the user sees fit.

7. Make sure every installed council member and bot sets up their scheduled tools, routines, and automations: recurring sweeps, planning sessions, check-ins, and loops, so they activate on their own and do everything their skills say they should. Offer the council's shared weekly rhythm (the Monday stand-up, weekly bookends, and the wandering gossip loop) from the council skill as the default calendar.

8. Finally, brainstorm ways the user can expand, remix or improve on this system for their own projects and goals. Offer to recruit and design new council members.
```

Polish is a skill to reduce slop then imbue art, and high craft.

The polish skill is one of the most abstract and unusual in this collection, but also one of my favorites. 

Use it to brainstorm ways to improve things. Great for when planning or reviewing.

It consists of 3 parts

- Goal
- Token List
- Outro

The token list is the core of the prompt, it's a list of values and words used to nudge your agent into specific headspaces and token distributions

The version presented here is very minimal. My full list is about 10x longer, so far.

You will need to customize this skill and write your own token list for maximum effect.

### Tiramisu Task Decomposition (1b.2)

🍰 /grim:dev:tiramisu-task-decomp 🍰

![tiramisu task decomposition](skills/dev/tiramisu-task-decomp/assets/tiramisu-icon-med.png)


| [Tiramisu](skills/dev/tiramisu-task-decomp/SKILL.md) |               |
| ---------------------------------------------------- | ------------- |
| **Difficulty**                                       | 🟪🟪🟪 Pro    |
| **Invocation**                                       | **🪄 Manual** |


Takes a plan and organizes it based on dependencies into parallel lanes of work.

This is named Tiramisu because I learned about this concept ages ago from a post that used a Tiramisu recipe example, and it stuck with me. So now you get stuck with it too.

[What's Functional Programming All About?](https://www.lihaoyi.com/post/WhatsFunctionalProgrammingAllAbout.html) by Li Haoyi

You don't have to read that, here's the short version:  
every recipe in every cookbook you have ever read is wrong. I'm so sorry.

You are giving your AI agents shitty recipes with the same problem.

Incorrect way to write a recipe (the imperative cookbook way):

```text
4 large egg yolks
1/2 cup granulated sugar (plus 2 tsp for the espresso)
1/2 cup sweet Marsala wine
16 oz mascarpone cheese
1 cup heavy cream
12 oz prepared espresso
about 40 ladyfingers
2 tbsp cocoa powder

1.  Dissolve 2 tsp sugar into the espresso and chill it
2.  Whisk the egg yolks
3.  Add the sugar & Marsala wine, blend
4.  Whisk the mixture over steam until thick & smooth
5.  Beat the mascarpone until creamy
6.  Whip the heavy cream to soft peaks
7.  Combine the custard with the mascarpone, beat until smooth
8.  Fold in the whipped cream
9.  Soak each ladyfinger in the espresso for about 1 second
10. Assemble the layers: soaked ladyfingers, cream, ladyfingers, cream
11. Sift cocoa powder on top
12. Refrigerate for 4 hours
```

Correct way to write a recipe (the functional dependency graph way):

```text
12 oz espresso + 2 tsp sugar -> dissolve -> chill ──────────────────────────────────────────┐
~40 ladyfingers ────────────────────────────────────────────────────────────────────────────┴─ soak 1 sec each ─────────────┐
4 egg yolks -> whisk -> + 1/2 cup sugar & Marsala -> whisk over steam ────────┐                                             │
16 oz mascarpone -> beat until creamy ────────────────────────────────────────┴─ combine ───────┐                           │
1 cup heavy cream -> whip to soft peaks ────────────────────────────────────────────────────────┴─ fold ────────────────────┤
                                                                                                                            └─ assemble 2x layers -> sift cocoa -> refrigerate 4 hrs -> Tiramisu
```

![tiramisu dependency graph](images/tiramisu-dag-infographic.jpg)

The fancy technical term for this is a DAG or Directed Acyclic Dependency Graph. 

I call it "/tira" 

Using tiramisu breaks down and decomposes complex plans into steps, lanes, handoff points, and lets you fan out lanes of subagents in parallel. 

This is ESSENTIAL and saves SO much time when running agent swarms or doing big changes and refactors.

*Usually you want to use this after a few round of brainstorming a plan first*

```text

```

### Model Quirks (1c.4)

🎭 /grim:dev:model-quirks 🎭

![model quirks](skills/dev/model-quirks/assets/newmodelquirks-icon-med.png)


| [Model Quirks](skills/dev/model-quirks/SKILL.md) |               |

| **Difficulty**                                   | 🟪🟪🟪 Pro    |
| **Invocation**                                   | **🪄 Manual** |


Every new AI model does something weird. 
Delve, em-dash, lots of lists, Yes, absolutely!, etc.

New models come out almost every week!

This skill is a simple mechanism to quickly rotate model specific prompts in and out of your AGENTS.md, skills and other prompts.

So you can easily adjust your agent to new model releases.

It helps mitigate model weirdness, annoying tendencies, and odd changes when upgrading models.

The mitigations themselves are applied inline as normal, unlabeled prompt text. Your prompts stay clean. 

A reverse-index ledger records the exact text of every change and which model it was for, so you can verify, prune, or undo any of it later after the next model release.

This way GPT 5.1's quirks and prompt changes don't end up in your GPT 6.0 prompts a year later when you aren't even using 5.1 anymore.

Separate your core prompt logic, from AI's quirks.

Currently enabled mitigations (full ledger: [docs/model-quirks-ledger.yaml](docs/model-quirks-ledger.yaml)):

- `claude-opus-5` - talk less, keep replies concise by default
- `gpt-5.5` - don't over-correct away from playful creature language (goblin mode stays ON)


```text

```

*The ledger makes cleanup safe*


## Expansion Packs (1d)

![expansion packs](images/expansion-packs-icon-med.png)


| [Expansion Packs Guide](docs/expansion-packs.md) |            |
| ------------------------------------------------ | ---------- |
| **Difficulty**                                   | 🟪🟪🟪 Pro |


Expansion packs is a system for handling LOTS of /skills. 
Like hundreds or thousands of them.

If you're reading this, there is a good chance you have a bunch of skills already, and I'm sure it's a giant mess.

The /grim: namespace and expansion pack system makes it super easy to organize your skills, and to view and interact with them using the dashboard, /grim:council:dashboard

There are easy tags to differentiate:

- `grim:` - the Tome's own namespace (make your own: `myName:`, `ABC-stack:`, ...)
- `ep:` - imported expansion-pack skill, unmodified third-party
- `mx:` - mutated fork of an imported skill
- `beta:` - new installs & experiments; manual-only until proven
- `og/` - the mirrored unmodified upstream copy inside a pack's folder

These let you tell at a glance:

- What skills are from the system, harness, MCPs or plugins.
  - Hopefully the vendor namespaced them, but unfortunately almost no one does this.
- What skills are yours
  - `/grim:` or your own `/myName:`, `/ABC-stack`, etc
- What new skills are still being tested
  - Using a `:beta:` namespace tag segment like `grim:beta:<skill>`  
  - Beta skills stay manual-only, no agent-auto use allowed.
- What skills you imported/remixed from others,
  - Each expansion pack imported third party skill is marked with `:ep:` for example `/grim:ep:grill-me`
  - Each skill that is mutated is marked with `ep:mx:` for example `/grim:ep:mx:grill-me`

The system also includes source links back to the original skill, and mirrors the original copy of a skill so you can easily track both your version of a skill, and the original skill. This lets you easily merge and semantically integrate future skill updates without losing your details and changes.

I find this setup makes it SO SO much easier to manage the huge amount of skills I am now playing with. I only expect AI to grow and get more powerful. So the more skills I can manage the better!

Currently installed example pack (full pattern & folder layout: [docs/expansion-packs.md](docs/expansion-packs.md)):

- [mattpocock](expansionPacks/mattpocock/) - [grill me](https://github.com/mattpocock/skills) by Matt Pocock
  - `/grim:ep:grill-me` - the unmodified original: grills you in frontier rounds of numbered questions, each with a recommended answer
  - `/grim:ep:mx:grill-me` - mutated fork: rounds capped at 10 questions, and skipped questions accept the recommendation

Use it as the reference shape when installing your own packs.

If you want suggestions for expansion packs outside of Grimoire's Tome, see the [Appendix](#appendix) 

─────────────────────

*Install a single skill:*

```text
install this skill as an expansion pack
https://github.com/mattpocock/skills
```

*Install a whole stack at once:*

```text
install this entire stack of skills as a single expansion pack, and disable them all by default
```

*Fork one into a mutation:*

```text

```

# Chapter 4: Workbench Artifacts

![Chapter 4: Workbench Artifacts](images/06-ch4-workbench-artifacts-flat-imagen.jpg)

∿∿∿ ✧ Chapter 4: Workbench Artifacts ✧ ∿∿∿


| Difficulty | 🟪🟪🟪 Pro |
| ---------- | ---------- |


You are likely already familiar with the artifacts paradigm, originally popularized by Claude Artifacts.

If not, short version, artifacts uses LLMs to quickly generate code to make small websites and interactive pages.

A plain artifact is one self-contained HTML file: the agent generates it, you open it, done. The Tome's standard for those is `/grim:artifacts` below. Sometimes you will run more complex pages which can use more files and local servers.

Workbench artifacts are an extension to artifacts, which combines:
artifacts + /skills + 3 new things

1. A text file data layer
  - so that coding agents can interact with the artifact without editing the template artifact directly
    - usually this is specially formatted .md files or .json files
2. A 2 way sync engine between artifact and the data layer
  - which hot reloads both the artifact and file, so underlying files and UI stay synced, when either one changes
3. Optional, Artifact compatibility and callbacks into a browser, host super app, annotation tools, or an artifact shell app of some kind.

The big benefits are

- Allowing coding agents to simply do their thing and make quick text file changes, without spending time or tokens fully regenerating artifact UI. The artifact auto updates as the agent works. 
  - For example as soon as the agent generates an image, it appears in the review surface.
- The reverse also works, the artifact can dynamically update the underlying files, and therefore the agent. Put another way, this gives the agent live visibility into the current UI state.
  - For example, if you heart an image in the image review workbench, you can then ask the agent to find all hearted images.
  - Or when using the grill me workbench, this allows the agent to read all your answers that you wrote in the artifact.
  - Tip this can be very handy when combined with polling, you can prompt the agent to do something based on you interacting with your artifact, and having the agent watch for state changes.
- This also allows convenient prompt ergonomics
  - for example instead of needing to prompt "take the 5th image you generated and change it to", I can simply click the annotate tool, click the image and say "change it", or click a button to copy "image 5" to the clipboard

Here is an example

```text
mySkill.md
myArtifact.html
myArtifact.css
myArtifact.js
myArtifact.py
files/saveFile.md
```

And how the data flows through it:

```text
   mySkill.md ─── teaches the agent
       │          the data format & workflow
       |
       ▼                annotations, screenshots
┌──────────────┐        & feedback callbacks    ┌────────────────────────────────┐
│ coding agent │ ◄───────────────────────────── │ super app / browser harness    │
│              │                                │  ┌──────────────────────────┐  │
│              │                                │  │ artifact UI              │  │
│              │                                │  │ myArtifact.html .css .js │  │
│              │                                │  └──────────────────────────┘  │
│              │                                └───────────────▲────────────────┘
│              │                                                │ 2-way hot sync
│              │                                ┌───────────────▼────────────────┐
│              │                                │ data plane / sync engine       │
│              │                                │ myArtifact.py                  │
│              │         writes & reads         └───────────────▲────────────────┘
│              │         plain text                             │ watches & writes files
│              │                                ┌───────────────▼────────────────┐
│              │ ◄────────────────────────────► │ raw files                      │
│              │                                │ files/saveFile.md              │
└──────────────┘                                └────────────────────────────────┘
```

Either side can change things: the agent edits the save file and the UI hot-reloads; the user clicks around the UI and the save file updates. Neither ever touches the artifact template code. And when the harness supports it, annotations and screenshots flow back to the agent as feedback.

## How to Cite the Tome (0.0)

Every skill and council member is a numbered verse. Headings show the display name first, with the verse number in parentheses, like `Model Quirks (1c.4)`. Cite them chapter-category.verse, like scripture:

- Grimoire's Tome 1c.4, Model Quirks, /grim:dev:model-quirks
- Midas (2b.3)

The letter is the category inside the chapter (1a Everyday Spells, 1b Dev, 1c Agent Ops & Working with Agents, 2b The Merchants Guild, ...). Verses only ever renumber inside their own category, and new categories append new letters, so old citations survive new additions.

Use ranges for groups (`Tome 2b.1-3`, the Merchants Guild).

For an exact, frozen quote, pin a version: `Tome 1c.4 @ v1.0` (or a commit hash).
